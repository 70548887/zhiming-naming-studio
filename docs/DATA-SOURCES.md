# 本地资料来源与重建

本项目的字义、读音和古籍引文来自实际下载的资料。生成式 AI 不负责编造字典条目。固定版本与各原始文件的 SHA-256 保存在 `data/source-lock.json`，构建结果及字段校验结果保存在 `data/build-verification.json`。

1.0.20起提供的可选真太阳时另用`data/solar-time-source-lock.json`锁定NOAA公式、必要原句、独立数值参考与署名说明，不混入命名字库版本。经度东正西负，实际UTC加经度修正及均时差；默认民用时间，原出生记录保留。具体口径、来源许可和验收状态见[SOLAR-TIME-SOURCES.md](SOLAR-TIME-SOURCES.md)。

## 清洗与质量门槛

1. 使用人工选定的命名字候选名单 `data/naming-characters.txt`；名单本身不作为词义来源。
2. 读取 Unicode 的 `kMandarin`、`kTotalStrokes`、`kTraditionalVariant`、`kSimplifiedVariant`、`kRSUnicode` 与 `CJKRadicals.txt` 固定文件；部首取实际汉字，如“水”“艸”，不是部首序号。
3. 按名单字及其繁体查找 MOE 的普通话异读条目，逐个读音保存其原有义项，未找到时查询中文维基词典；没有可关联的读音与直接中文义项时明确排除。可用`dictionaryWord`明确选取Unicode字形候选内的原词条；不允许指向无字形关系的任意词。松指定MOE“松”而非“鬆”，保留松科植物的原释义。MOE 的“(一)之又音／语音”等只有在原词条明确给出编号对应关系时，才关联同词条对应义项。
4. 默认读音优先采用 `data/naming-editorial.json` 中有来源支持的姓名用法，否则按 Unicode 读音匹配 MOE，最后采用可核对的源读音。默认显示至多三项对应读音的原义，完整各读音原义保存在 `readings`；原文逐字保留，不翻译、不改写、不重新许可为 CC BY-SA。
5. 多音性质由结构化 `polyphonic` 与 `readings` 参与音韵评价；普通笔画、Unicode 简繁和异体关系分别保留来源。避字以这些等价关系及 NFKC 处理，避免“遠／远”“寧／宁”漏检，不改动存储的真实姓名。
6. 六十四卦必须有 64 个不重复卦号、64 卦辞、384 爻辞和 64 大象；《诗经》按原文件篇章导入。
7. 所有记录唯一标识和来源链接通过检查；逐字、逐读音精确比对原始义项，默认义项必须属于默认读音。合格命名字少于500个时构建失败。修订数据包`2026.10.18.1`包含779字、1,833引文、433条固定知识，140个字有多个源读音。应用另载120条逐月原文，合计553条知识，不能将此汇总数误记为基础SQLite条目数。

“核对”在此指来源字段逐项、结构和引文一致性的自动检查。没有把程序检查描述成独立姓名学专家对每个字的审定，工作台仍提供人工修订。字典释义可能包含多义、旧义或不适合单独作姓名寓意的义项，生成器应结合上下文与家庭要求选择，起名师应审阅报告。

## 命名选义与典籍上下文

字典原文和项目原创的命名意象分开保存。生成器不再把首个字典义项自动拼成祝愿：“安然”的解释采用从容安适，“知微”采用细察事理，字典中的“燃的本字”“隐藏”等原义仍可查看。没有命名选义记录的字明确显示待起名师复核，不能把原义自动美化。

`data/naming-editorial.json`目前登记40条引文选用规则，覆盖44个名字：34个原文连续出现、10个选字重组。每条绑定完整引文`id/sourceId/title/chapter/text`、指定摘录、可用姓名组合、默认读音和选义语境。构建及新生成入口逐项精确匹配；同ID但换来源、标题、章节或全文也不沿用已审出处。只有对应关系全部满足，才展示“典雅有出处”；其余字面共现只属于知识检索资料，不作为名字出处或出处排序依据。

本轮新增26条规则、27名，经过对应原篇全文及独立语义复审，细目见[命名出处审阅](NAMING-CITATION-REVIEW.md)。例如“予和”不会引用“倡予和女”来证明“给予和善”，“乐安”不会引用被弃语境，“宁”不会从“不宁方来”推为安宁。重新组合的字明确说明并非原文连词。与已审出处绑定的组合解释使用该句原义和现代家庭期许，避免“攸=所”“景=大”“纯=充盛”“丽=附丽”等被全局命名意象覆盖；没有精确出处匹配时，不继续发布其绑定解释。这些说明是项目编写的语言审阅，不冒称古籍原文或姓名学专家认证。

厚、自、强、升、慎五个新增字分别采用固定MOE原词条及对应拼音，使厚德、自强、允升、淑慎可实际生成。普通字形笔画不用于补造康熙计数；厚9、自6、升4已在1.0.23从同一固定康熙部首CSV补齐；当前779个命名字均有候选，分歧仍需确认，旧方案不回填。旧方案依生成时完整知识包核验，保留原解释、评分和来源快照，不用当前命名规则重算。

本轮完整回归98文件、750项通过。另以实际命名入口核对27个新名、4个补字旧名及155种引文五字段篡改，验证出处与组合解释匹配、失配后撤销及待审提醒回退；永久8项Store升级测试保留真实旧包的全部候选字段、来源、历史、备份与报告HTML。这些检查不代替全文语义复审，也不将新版桌面安装或PDF导出记为已验收。

## 汉字五行与笔画的边界

`CharacterEntry.elements` 是项目自编的字形／字义意象参考标签，例如木、水、火、金等直观意象；`elementBasis` 会标明其性质。未能给出明确意象的字保留空属性。标签不是古籍公认的唯一汉字五行，不是康熙数理。`strokes` 为 Unicode 普通字形笔画，不得用于冒充康熙笔画数。

生肖字根、喜用判断、奇门排盘由版本化规则引擎处理，不从字典资料中自动“推知”。本知识库的奇门内容是基础符号与当前流派说明，不伪称包含全部奇门典籍。周易收录内容不代表完整《十翼》。

## 重建命令

在项目根目录运行：

```powershell
npm install
npm run data:build
```

已有原始快照时离线重建：

```powershell
node scripts/build-data.mjs --offline
node scripts/build-data.mjs --offline --reproducibility-check
```

构建过程是“固定 URL 获取 → 原始快照保留 → SHA 校验 → 数据清洗 → 引用和字段验证 → SQLite 与 JSON 原子写入”。下载自动优先 IPv4，单个失败最多重试两次。解包需要 Windows 系统自带 `tar`；没有该命令会明确失败，不输出伪成功。

第二条命令比较本次和上次的 JSON、SQLite 字节校验值，生成 `data/reproducibility-verification.json`；不一致时明确失败。先修改了构建脚本或选义资料时应先普通构建，再执行重复构建检查。

当前`2026.10.18.1`已完成离线重复构建，JSON、SQLite前后字节一致；SQLite SHA-256为`f264eb26f631441a31324e9be14058f38d02d444070e00e9e0690b4f0b9ff7cc`。显示版本与应用按完整原包摘要前12位取得的资料版本分别保留；不把文件名或显示版本当作完整性凭据。

产物 `data/dataset.json` 与 `data/knowledge.sqlite` 具有相同数据。SQLite 的 `characters`、`citations`、`knowledge`、`sources` 四表以 `id TEXT PRIMARY KEY, json TEXT NOT NULL` 储存；另有 `metadata` 版本表。客户数据库与本知识库分别保存。

数据包更新需要保留原快照锁文件并在单独目录建立新版本，比较来源、许可和校验结果后再导入应用；不要删除锁文件来掩盖校验失败。
