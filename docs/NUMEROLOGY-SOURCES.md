# 康熙笔画候选数据来源与适用边界

当前版本：`kangxi-radical-candidates-2026.10.19-v2`。构建日期：2026-10-19。旧版`kangxi-radical-candidates-2026.10.18-v1`以冻结候选和来源锁保留，历史方案按生成时版本核对。

本数据包提供可追溯的**字形及计数候选**，供起名师选择后计算五格；它不把简繁映射或任意电子表的数值自动定为唯一姓名学笔画。普通字库的 `strokes` 字段仍然只表示普通笔画，不参与本模块。

## 实际采用的来源

### 1. 康熙部首计数表：MIT

- 仓库：[breezyreeds/kangxi-strokecount](https://github.com/breezyreeds/kangxi-strokecount)。
- 固定提交：`778d23d0566066ab19906557755b882818ec0a06`。
- 原始文件：`kangxi-strokecount.csv`，63,696 行字形，原文件包含 MIT 及作者 Kawai Lo 的声明。
- 原始字节 SHA-256：`2564b8b8738bd06ffe83a26e6dd791df98aefc9feb4d1b01b3d0c412b54ae1c8`。
- 原文件及 README、MIT 全文保存在 `data/raw/numerology-breezy-*`，下载后设为只读。

作者将其定义为“按康熙部首计算的笔画”，并给出「華」按艸部6加部外8为14画的说明。它与现代手写笔画、普通繁体笔画不同。本项目逐行保留其数值和 CSV 行号，不把数值重新写成项目自算值。

该表还包括现代简体等字形。63,696 行不是本项目证明的《康熙字典》独立收字数。比如「陈」在表中13画，「陳」16画；前者不能自动替代选用「陳」的姓名学惯例。界面须展示字形、计数和来源，并让起名师确认。

### 2. 电子《康熙字典》原文：MIT / 原典公有领域

- 仓库：[shunshi-ai/kangxi-mcp](https://github.com/shunshi-ai/kangxi-mcp)。
- 固定提交：`fad0bdf7c34b0ec555edbb2af91db737825a4beb`。
- 采用文件：`packages/kangxi-core/data/kangxi-text.json.gz`，17,034 条电子原文。
- 原始压缩字节 SHA-256：`848ccee01f42f7d4a5ffb51888cba38c82be2e77950eaf1aba1278ee98373236`。
- 原文件、README 和 MIT 全文保存在 `data/raw/numerology-shunshi-*`，下载后设为只读。

它用来补充原文条目位置以及头部明确的「康熙筆画」证据。若原文没有明确总笔画，本构建不会从释义或部外文字猜数。原文明确数值与部首表不同时，额外保留一个有独立 ID 的候选。

已核对的差异是「王」：部首表给4画，电子原文头部为「【午集上】【玉字部】 王 ·康熙筆画：5 ·部外筆画：0」。本项目保留4与5两个来源候选，展示待确认，不擅自修正或称任何一种为通用姓名标准。起名师采用常见姓名学王4时，方案记录所选的部首表版本。

**未导入该仓库的现代 `chars.kx` 姓名表。** 上游已说明其现代姓名笔画与原字原文有不同规则；实查还存在「万」现代主条15与「萬」镜像条13的差异。避免把现代折叠结果冒充其原字形的独立原典证据。

### 3. 简繁候选关系：Unicode-3.0

- 仓库：[unicode-org/unicodetools](https://github.com/unicode-org/unicodetools)。
- 固定提交：`4fd8eca90b30aa4c72543ccddb4c15d05becdf8d`，Unicode 17.0。
- 复用现有已锁定原文件 `kTraditionalVariant.txt`、`kSimplifiedVariant.txt` 及 `unicode-LICENSE`。
- 用途仅为展开全部关联字形；`发` 保留 `发 / 發 / 髮`，`于` 保留 `于 / 於`，`后` 保留 `后 / 後`。

Unicode 关系不判断姓名语义。一对多或单一转繁都不意味着系统已经替用户选择，映射说明随每条记录保存。

**未使用 `kTotalStrokes`、`kRSUnicode` 或旧 `kRSKangXi` 计算姓名学康熙笔画。** `kTotalStrokes` 是普通笔画；`kRSKangXi` 属部首索引/部外笔画信息，字段名称本身不能证明姓名学计数。普通笔画、索引和本次选用的字形计数来源必须区分。

## 覆盖与数据合同

构建输入为当前779个命名字、它们的字形、《百家姓》的姓氏用字以及独立例名所需的「一」等字；这些文本只是查询词表，不是笔画来源。当前共覆盖1,452个输入字，生成2,255条候选记录；779/779命名字有候选，240个命名字含多字形或多计数。覆盖数和来源差异保存在 `data/numerology-source-lock.json` 的 `build` 字段。

此次只增加3条固定源候选：

| 输入／字形 | 固定部首表计数 | 原CSV定位 |
| --- | ---: | --- |
| 升／升 | 4 | L1350：`U+5347,21319,升,4` |
| 厚／厚 | 9 | L1432：`U+539A,21402,厚,9` |
| 自／自 | 6 | L13182：`U+81EA,33258,自,6` |

先前“厚、自、升缺康熙来源”实际是康熙候选包仍按774字词表构建，未随779字词表重建。三字早已存在同一固定CSV及电子原文，未引入新网络资料。电子原文字头只给部册、字部和字形，没有明确「康熙筆画」总数，因此9／6／4仅归固定部首表，不伪称电子原典头部独立给出同数，也不从普通笔画补算。“强、慎”因原姓氏查询词表已在旧候选中，当前字库增加它们不需另造记录。

旧2,252条记录的ID、字形、计数、来源、定位及说明逐字段保留，来源元信息和所有固定原件字节不变；新增3条不是批量重映射或自动替用户选择简繁。王4／5、强／強等分歧继续需要按现有规则确认。

输出 `data/numerology-strokes.json` 包含 `version`、`sources`、`records`。每条记录包含：

- `id`：稳定的来源/输入/字形/计数标识；
- `character`：实际输入字；
- `glyph`、`count`：这个来源记载的候选字形及计数；
- `sourceId`、`sourceLocator`：来源及 CSV 行号或 JSON 字头位置；
- `note`：映射、来源差异及需要复核的说明。

多候选不按出现顺序选择，不把同计数的不同字形合并为一个已确认字形。缺字保留其他起名功能，五格保持待确认，不能用普通笔画补位。

## 构建与核验

首次构建下载固定提交的文件；已有原文件按锁定哈希读取，不访问 GitHub：

```powershell
node scripts/build-numerology-data.mjs --offline
node scripts/build-numerology-data.mjs --verify --offline
```

明确首次联网构建时仍可不带`--offline`，只取缺失的固定提交原件；本次全部复用已缓存原件。`--offline`遇缺原件即失败，不尝试网络或普通笔画后备。当前查询词表有任一命名字缺固定候选时，构建失败而非静默发布部分覆盖。

下载采用 IPv4，并以临时文件加重命名写入；原始文件设为只读。源地址、提交、字节大小、许可证与 SHA-256 逐文件锁定；Unicode 文件同时核对主数据锁。任何已锁来源变化都会失败。

`--verify`不改数据文件，重新解析固定来源并逐字节比较产物及来源锁，同时验证63,696个计数条目、17,034条电子原文的固定大小、码点／字形一致性、计数合法性、来源声明及779个命名字全部覆盖。本次离线重建和再解析验证的输出字节一致，验证前后产物和锁均未改写；缺失缓存的独立隔离检查也在下载入口前失败。当前候选产物SHA-256为`c218bb3e9b496fd7be3e517990c6cdedd1d9d1726e81c9a2f0285f86bab8964c`，当前来源锁SHA-256为`600feb5251986fe5e91c82d27bc1503e9626f4c1f78be61f8f1a4bcc51b2ab02`。

旧v1候选SHA-256仍为`08fff8673a3a22fe568a65d203fdd7545a725ebe0251898f7a5b3fead71963d6`，与旧来源锁一并保存在`data/numerology-history/kangxi-20261018-v1/`。已知v1历史方案按该冻结来源核验，不因当前新增覆盖而自动给原先缺字补数、移除81分类或改写审阅；主动重新确认笔画才按当前数据生成新修订。未知历史数据版继续保留既有“未在当前安装包重新核对”的提示，不把未知旧版本伪装成v1或v2。历史恢复及发布验收以对应实测记录为准，本数据说明不预先声称未执行检查完成。
